# ADR-0010: Footprint Geometry and 3D Models Do Not Enter the Language; the Project's Self-Built Footprint Library Is a First-Class Artifact

Status: Accepted
Date: 2026-10-20
Impact: `AGENTS.md` §4.5, §8, §9; `schemas/ir/v0.1/project.schema.json`; new `docs/footprint-authoring.md`

**Later decision**: [ADR-0029](0029-package-code-footprint-and-3d-model-ownership.md) amends the
placement of 3D models — a model belongs to a `part`, not to a footprint, because a land pattern
is vendor-independent while a body is not. Decision 1 of this record (no dimension fields in
`.teda`) stands unamended, and decision 5 below still holds: a model is a reference to a CAD
file, and the file lives in the library tree under the library's `content_hash`.

## Background

Two facts sit side by side:

1. **This project's boundary**: `AGENTS.md` §1 explicitly states "we are not component library maintainers (we borrow the KiCad symbol library and JLC part numbers)"; the `component` file only records `mpn` / `package` / `symbol` / `footprint` (`lib:name`) and the pin table, **geometry is not in the language**.
2. **A new fact**: an agent needs only a few minutes to build a footprint (including a 3D model) from a datasheet, and humans are hand-writing footprints doing the same thing. In other words, a "library" is no longer only an external dependency borrowed from upstream; it can be **a project-owned artifact generated by an agent**.

So the question becomes: now that footprints and 3D models can be produced on a whim, **should 3D dimensions be written into `.teda`** (letting the board carry its own geometry)?

## Decision

### 1. Footprint geometry and 3D models do not enter the language

- There are **no** fields in `.teda` for pad dimensions, courtyard, assembly outline, 3D dimensions, and none will be added.
- The reasons:
  1. **Wrong ownership layer**: footprint geometry is a property of the *component type* (the same 0402 is the same geometry on ten boards), not a property of *this board*. Writing it into the board description = copying the library into every board, which is exactly an amplified version of the "duplicate description" pitfall in `AGENTS.md` §7 ("the same connection written twice, change one place and miss another").
  2. **The reference point already exists**: `component.footprint` (`lib:name`) is the single reference point to the geometry (§4.5). The geometry should land in the library, not in the description.
  3. **3D even less so**: STEP/WRL is CAD data, not diffable text; it is referenced by a pointer in the
     `part` or `family` file ([ADR-0029](0029-package-code-footprint-and-3d-model-ownership.md)
     decision 2), and describing the model itself in the language would create a second source of
     truth. The exported KiCad footprint carries no model at all — the land pattern is 2D.
  4. **Layering**: `AGENTS.md` §3 classifies the 3D assembly view as B1 (derived, free to change), while board-level physical facts are B0 (not free to change). The dimensions of the component body belong to the component library, not to board-level facts.
- **The dimensions that belong at board level are already in the language**: `board_thickness`, `stackup`, `rules` (clearance/trace width/solder mask/solder paste/thermal pad), the coordinates and rotation of `place`, and the mounting holes and cutouts of `physical_only`. The only thing missing is "which footprint does this board use", and that is given by `component.footprint`.

### 2. The project's self-built footprint library is a first-class artifact

- Library sources come in two kinds, with a unified reference form `lib:name`:
  - **Borrowed**: the KiCad official libraries, the JLC libraries — `libs.<name>` records `source` + `rev`/`version`.
  - **Self-built**: a footprint library under the project directory (a `.teda` footprint description written by an agent or a human + optional 3D models; the format is described in `docs/adr/0011-library-format-and-footprint-ir.md` and `spec/footprint.md`) — `libs.<name>` records `path` (the project-relative library directory) + `content_hash`.
- The **version lock of a self-built library uses a content hash**: `content_hash` = SHA-256(concatenation of `<relpath>:<file_sha256>\n` for all files under the library directory, sorted by relative path). Same shape as the shard aggregation in [ADR-0008](0008-ir-shard-identity-and-hash.md) decision 5, for the same reason: even without an upstream rev, you need a reproducible version anchor.
- Landing point: the project carries an `fp-lib-table` (KiCad reads it to resolve `lib:name`), pointing at the **exported** `.pretty` directory ([ADR-0011](0011-library-format-and-footprint-ir.md) decision 4). The first trial run has already proven that this is a hard requirement — without it KiCad reports `lib_footprint_issues` for every footprint (`docs/kicad-pcb-format.md` records this).
- When `component.footprint` references a self-built library it is written as `project:<name>` (the prefix is free, e.g. `project:sot-23-5`); the IR library reference format allows any `<prefix>:<name>` (the `library_ref` in `schemas/ir/v0.1/common.schema.json`).

### 3. Checks that generated footprints must pass

The tools (checker + KiCad DRC) are responsible, not manual review:

1. The footprint exists, the library table is parsable, and `lib:name` resolves to a concrete `.kicad_mod`;
2. **the pad number set ⊇ the schematic pin number set**: one missing → error (already settled by `AGENTS.md` §4.4 rule 2); one extra → warning;
3. Pad geometry passes DRC (clearance/solder mask/solder paste), and the KiCad-side rules are still provided by `.kicad_pro` ([ADR-0005](0005-manufacturing-output.md) decision 1);
4. The assembly level (courtyards not overlapping, 3D consistent with the footprint origin/orientation) belongs to **B1 derivative checks**, looked at through the 3D preview; it does not enter the language and does not enter the IR.

### 4. Mechanics and structure do not enter the language

- **Cross-domain constraints** such as enclosure interference, connector mating space, and cooling airflow do not enter `.teda`: `AGENTS.md` §1 already declares that phase one does not describe enclosure structure.
- If we want to express them in the future, we need a separate `structure` description layer and an ADR; they must **not** be stuffed into the `pcb` description as a patch. `physical_only` in `pcb` only covers in-board entities (mounting holes, fiducials, test points, stitching vias, cutouts).

## Consequences

- **The language surface is unchanged**: no fields are added to `.teda`, and the parser/IR are untouched; the only exception is that `libs` entries gain two keys, `path` / `content_hash` (the IR and `project.toml` stay in sync). The footprint itself is an **independent library artifact** (the `footprint` kind) and does not enter the board description; see [ADR-0011](0011-library-format-and-footprint-ir.md).
- **Libraries change from "external dependency" to "project artifact"**: a project can be entirely self-sufficient (the KiCad official libraries are only a convenience), and that is decisive for "an agent completes a board on its own" — provided footprints can be generated automatically and checked (decision 3).
- **Reproducibility relies on the content hash**: a change in a self-built library (`.teda` source or 3D model) → `content_hash` changes → the artifacts have to be re-exported; that is exactly what we want (if the footprint changed, the Gerbers and the 3D obviously have to be re-exported).
- **3D still does not participate in any determination**: 3D is an input for review and assembly checks; it does not participate in connectivity and does not write back to IR (`AGENTS.md` §2 rules 2, 3).

## Follow-up

- `docs/footprint-authoring.md`: the workflow for an agent to author footprints, the file layout, the `fp-lib-table` syntax, and the checklist.
- Whether **symbols** in a self-built library follow the same mechanism (`component.symbol` pointing at a self-built `.kicad_sym`) — we lean toward yes, but we have to confirm whether KiCad's symbol library table and footprint library table are the same mechanism.
- How 3D models are attached and hashed: once a self-built library uses our format, the 3D models live inside the library directory (`assets/footprints/project/3dmodels/…`) and are covered by `content_hash` as well (change a model and the hash changes). The format is described in [ADR-0011](0011-library-format-and-footprint-ir.md).

## Addendum (2026-10-20): a self-built library has two roots

After [ADR-0012](0012-symbol-description.md), a self-built library provides both symbols and footprints, and the two share the same `<lib>:` namespace. `[libs.<name>]` therefore allows two root keys:

```toml
[libs.project]
source = "project"
symbols = "symbols/project"
footprints = "footprints/project"
content_hash = "…"
```

A library with only one root may still write `path` (the old form). `content_hash` covers all roots: SHA-256(concatenation of `<project-relative path>:<file_sha256>\n` for all files, in byte order), computed by the tool `bun run lib:hash <dir>...`.

## Addendum (2026-10-22): the project's own assets are not a library

Amended by [ADR-0031](0031-project-tree-ownership-model.md) decisions 1, 2 and 6.

The "self-built library" of decision 2 is no longer a library. A library is a separate
repository that other projects depend on; a project does not publish its assets to anybody. The
project's own symbols and footprints are simply its assets, under `assets/symbols/` and
`assets/footprints/`, referenced by bare id.

Two consequences:

- **The content hash has one job left.** It pins a *vendored* library, whose bytes come from
  elsewhere and must be verified. The project's own assets need no hash of their own: their
  content is covered by the project hash, and a second number over the same bytes would be a
  second thing to keep in step.
- **The `project:` prefix becomes a legacy spelling.** `project:sot-23-5` still resolves and
  still means "this project's own asset", but a bare `sot-23-5` says the same thing, and the
  `project:` level inside `assets/symbols/project/` and `assets/footprints/project/` disappears.

The decision itself stands: footprint geometry and 3D models do not enter the language, and a
footprint library written in `.teda` is a first-class artifact.

## Addendum (2026-10-22): the exported footprint is 2D, and the model lives with the device

Follows [ADR-0029](0029-package-code-footprint-and-3d-model-ownership.md) decision 2 and its
2026-10-22 addendum, and amends decision 1.3 and the follow-up note about model hashing.

- **The model pointer lives in the `part` or `family` file**, not in the footprint file. A land
  pattern describes what the copper sees; a body describes what the solder sees.
- **The exported `.kicad_mod` carries no 3D model.** The KiCad output goes to a fabricator and at
  most to a reviewer, so it is a pure 2D land pattern — one land pattern, one file, no variants.
- **Where the models are hashed**: with the part or family that owns them, inside the tree that
  provides that part (the project, or the library that provides it), covered by that tree's
  `content_hash` — the same rule as the footprint sources themselves. A change to a model
  changes the hash and invalidates the artifacts, which is the intent.

## Addendum (2026-10-24): no content hash at all

Amended by [ADR-0047](0047-an-external-library-is-a-template-not-a-dependency.md) decision 7.

`[libs.<name>]` is withdrawn, and with it `content_hash` and `bun run lib:hash`. A project's own
assets are its own files under `assets/`: they enter the build identity as normative shards
([ADR-0023](0023-ir-layer-on-disk.md) decision 2), which is the same guarantee the hash provided
(a change changes the project hash) without a second number to keep in sync. The paragraph above
describing the two-root `[libs.project]` table is history; the two roots themselves
(`assets/symbols/`, `assets/footprints/`) are unchanged. The 2026-10-22 addendum's "where the
models are hashed" stands with "covered by that tree's `content_hash`" read as "part of the
project's normative shards".
