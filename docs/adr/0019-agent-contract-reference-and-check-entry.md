# ADR-0019: Contract Reference and Check Entry Point for Agents

Status: Accepted
Date: 2026-10-21
Impact: `packages/ir/scripts/generate.ts`, `packages/ir/src/units.ts`, `packages/cli` (`texteda check` / `compile`), `docs/ir-reference.md`

## Background

The main consumer of this project is agents (AGENTS.md §0: humans only review). An agent has to locate two things across a pile of files:

1. **What a given IR field is, and what its unit is** — today you can only dig through `schemas/ir/v0.1/*.schema.json` (JSON is hard to grep) or read `docs/adr/0008` (which describes conventions, not a field-by-field mapping).
2. **What is wrong with my project and how to fix it** — diagnostics have codes ([ADR-0016](0016-diagnostic-error-codes.md)) ✓, but there is no single entry point that aggregates "semantic-layer ERC + contract-layer schema validation" into one machine-readable result.

## Decision

### 1. The IR Contract Reference Is Generated from the Schema, Not Hand-Written

`docs/ir-reference.md` is generated by `bun run gen` from `schemas/ir/v0.1/`, one line per field: type, whether it is required, **unit**, description. The generator and the error-code document (`docs/error-codes.md`) are two outputs of the same script.

- The schema is the single source of truth; the document is a derivative (the same principle as the canonical JSON in [ADR-0004](0004-ir-representation.md)).
- The document **answers only two questions** (field type, unit) and does not restate the spec — that avoids a second copy of the spec that will drift. Behavioral semantics still come from `teda.md` and `spec/`; the document only points.
- Fields missing a `description` are listed in the coverage list at the end of the document; filling them in is **writing the contract**, not writing documentation, so it is worth doing.
- **Union types must be expanded**: for a `oneOf` like `constraint`, the dimension fields live in the branches (`min_uv` / `max_na`). Rendering only the top-level `properties` would make the very fields people most want to look up unlookupable, so the generator emits a table per branch, with `type=` in the heading.
- **The generator must enable `unreachableDefinitions`**: adding a sibling `description` to a `$ref` makes json-schema-to-typescript **inline** that reference, and named types such as `Slug` / `NetOrPinRef` disappear from the type surface (measured: filling in descriptions once killed 6 names, and the compiler only caught 1). With the flag on, every `$defs` produces a named type.

### 2. The Dimension Table Is Promoted to the IR Layer

The canonical units of the IR are determined by field-name suffixes ([ADR-0008](0008-ir-shard-identity-and-hash.md) decision 4): `min_uv` is voltage in µV, `value_mohm` is resistance in mΩ. This suffix table previously lived only in the parser (`packages/parser/src/quantities.ts`), so the generator could not use it. It is now promoted to `packages/ir/src/units.ts`:

- It describes the **convention for IR field names**, which is a contract, so it belongs in `packages/ir`;
- The parser and the generator share one copy (instead of each writing their own);
- `packages/ir` still has zero runtime dependencies (this table is pure data).

### 3. `texteda check` Is the Only Check Entry Point

```
texteda init <dir> [--force] [--name <project name>]
texteda compile <project dir> <board_id> [--json] [--out <file>] [--pcb]
texteda check <project dir> [--json]
texteda netlist <project dir> [--board <board_id>] [--json] [--out <file>]
```

`check` covers **all** boards in the project (`design/sch/<board>.teda`), parsing each board → semantic-layer ERC → contract-layer schema validation;

- Diagnostics use the unified payload of [ADR-0016](0016-diagnostic-error-codes.md) (`code` / `severity` / `location` / `data`); `--json` goes to stdout, the human-readable form goes to stderr;
- Exit code: 1 if there is an error, 0 if there are only warnings (warnings do not block the gate);
- A component file that cannot be read, and a component file whose header id does not match the file name (AGENTS.md §4.5), both count as errors.

`compile` and `check` share the same project-reading layer (`packages/cli/src/project.ts`), so layout knowledge lives in exactly one place.

### 4. The File System Is Confined to the CLI Layer

`packages/parser/scripts/compile-schematic.ts` is moved to `packages/cli` (`texteda compile`): it is a user command, not library code. Per [ADR-0009](0009-implementation-stack.md) decision 1, only the CLI/export layer may touch disk; leaving a command script in the parser package blurs the "library packages do not touch fs" boundary.

### 5. Diagnostics Carry a Stage: Parse / Contract / Design

The output of `check` must let an agent tell "the description is broken" from "the design has problems". The way to do that is to classify by **domain** into three stages (`parse` / `contract` / `semantic`), with `countsByStage` in the payload.

The key point: **the stage does not need to be declared at the call site**. The domain vocabulary is closed ([ADR-0016](0016-diagnostic-error-codes.md)), and a domain can only belong to one stage, so the mapping is a pure function (`STAGE_BY_DOMAIN`) and not a single line at diagnostic creation needs to change. This step is the precondition for F19 (moving the ERC rules into `packages/core`) — by the time the migration is complete, agents can already route by stage.

### 6. Fix Hints (`hint`) Are Registered in the Registry

The "how to fix" of a diagnostic previously existed only at the call site (scattered and unsearchable). Registry entries now carry a `hint` (how this code is usually fixed), while call sites may still give a more specific wording; when the payload is assembled, take "call site first, registry as fallback".

This way every row of `docs/error-codes.md` has a "how to fix" column, and an agent that gets a code can act directly without hitting the error once first. The registry remains the single source of truth (the code-table property of [ADR-0016](0016-diagnostic-error-codes.md) is extended to the `hint` field).

## What We Do Not Do

- **No generated SDK / client**: the IR is data (shape), the API is behavior (parse / compile / validate / format / emit). Generating interfaces from the schema would conflate "which fields exist" with "what can be done", and with no second consumer yet the generated API has no stability pressure. What is needed is a small hand-written facade ([ADR-0009](0009-implementation-stack.md)'s `packages/core`) + CLI + LSP.
- **No ERC rules as a rule language**: the rules stay in code (AGENTS.md §11 Q2/Q9: both expressions and generators were pushed back on). What needs to change is the **boundary** — the rules gradually move out of the parser and into core, so that third parties can tell "the syntax implementation is wrong" from "the design has problems".
- **No LSP yet**: that comes after core has stabilized.

## Impact

- `bun run gen` produces one more document; `bun run gen:check` still blocks drift.
- The implementation location of `bun run compile:schematic` has changed, but **the command name does not** (`bun run compile:schematic <project dir> <board_id>` still works).
- Two new diagnostic codes: `syntax.component-invalid` (component file fails to parse) and `ref.component-id-mismatch` (the component file header id does not match the file name).

## 2026-10-24 — The Contract Stage Covers Every Description the Shard Tree Serialises

Decision 3 listed the boards as `check`'s scope. In practice `check` also *reads* the project's
symbols and footprints — the drawing and coverage checks need their geometry — but it read them with
the failures silently dropped, and it validated the contract of the schematic, pcb, procurement and
system shards only. A project whose symbol or footprint did not compile was therefore green under
`check` and red under `texteda ir`, which refuses to write a shard that does not compile or does not
satisfy its contract. One gate said "fine", the other refused the same tree: the agent contract of
decision 3 ("`check` is the entry point") was broken in the one direction that matters.

`check` now applies parse + contract validation to every description the shard tree serialises:
`component`, `symbol`, `footprint`, and the print page (`schematic-view`). A file that fails is
reported and left out of the geometry the rest of the run sees — the same treatment `ir` gives it.

**Not** part of this, deliberately: reference resolution. A device may name a symbol or footprint the
tree does not hold yet — a logic-only project with no drawing is a legal state (AGENTS.md §4.2), and
`assets/symbols/` is empty when `texteda init` is done. A *missing* geometry file is therefore not an
error; an existing one that does not compile is.
