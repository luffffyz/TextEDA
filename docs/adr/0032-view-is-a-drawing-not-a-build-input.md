# ADR-0032: The View Is a Drawing, Not a Build Input

Status: Accepted
Date: 2026-10-22
Related: [ADR-0021](0021-schematic-view-layer.md), [ADR-0025](0025-flat-board-and-print-pages.md), [ADR-0023](0023-ir-layer-on-disk.md), [ADR-0031](0031-project-tree-ownership-model.md), [ADR-0008](0008-ir-shard-identity-and-hash.md), [ADR-0014](0014-reference-renderer.md)
Impact: `AGENTS.md` §3 (the S1 row), §4.2 (Print page, View), §9, §10; `spec/schematic-view.md`; `schemas/ir/v0.2/schematic-view.schema.json`; `packages/parser` (the `view` description type); `packages/cli` (`init`, `ir`); `packages/renderer`; `examples/reference-project/views/**` (after the move); `docs/backlog.md` F3 / F30

## Background

[ADR-0031](0031-project-tree-ownership-model.md) reorganised the project tree by ownership and
froze its shape. It left one thing open: the print pages.

A print page is a file under `sch/<board_id>/`, inside the directory of the description type
`schematic`. It is a different description type — its own spec, its own schema, its own parser
([ADR-0021](0021-schematic-view-layer.md) decision 1) — living inside another type's directory,
and it collides with its own board: `sch/hub.teda` and `sch/hub/` are two different things with
the same name.

Underneath the placement question there is a second one, which the hash rules of
[ADR-0023](0023-ir-layer-on-disk.md) decision 4 have never had to answer. That decision
classifies a shard as **normative** when the build depends on it and **advisory** when nothing
built depends on it, and it says that *board shards are always normative*. The board's shards
include its views. So today, moving a label in a print page changes the board hash and the
project hash.

That is wrong, and the reason is visible in the rules themselves: no artifact that is built from
the project depends on where a label sits. The renderer reads the view and draws it; the
exporter reads the logic; the netlist, the BOM and the manufacturing package never see a
coordinate. A reviewer nudges a label out of the way of another, and the signed manufacturing
package for that board stops matching the project. The classification criterion that
[ADR-0023](0023-ir-layer-on-disk.md) decision 4 states — *would changing this invalidate a
signed manufacturing package?* — answers the question on its own: a print page does not.

## Decision

### 1. Print pages live in their own root, beside the circuit and not inside it

```text
my-board-project/
├── design/                          # the circuit — the truth
│   ├── sch/<board_id>.teda
│   ├── pcb/<board_id>.teda
│   ├── modules/<module_id>.teda
│   └── system/<system_id>.teda
└── views/                           # the drawings — hand-written, discardable, not the build
    └── <board_id>/<page_id>.view.teda
```

This amends [ADR-0021](0021-schematic-view-layer.md) decision 1 and
[ADR-0025](0025-flat-board-and-print-pages.md) decision 4, which placed the page file next to
the board file.

- **`design/` holds the circuit and nothing else.** Every consumer that scans the circuit layer
  may assume that what it finds there is a circuit description. A print page is not one: it is
  discardable, rebuildable by hand or by an agent, and outside the build identity. Putting it in
  `design/` would force every one of those consumers to learn to skip it — the same mistake as
  putting a derived thing in a source directory.
- **The name collision disappears.** `sch/hub.teda` and `sch/hub/` no longer exist; the board
  file and the board's pages live in different roots, and no directory holds two kinds of thing.
- **The board grouping survives.** `views/<board_id>/` holds the pages of one board, one file per
  page, exactly as `sch/<board_id>/` did. Which pages a board has is still one directory
  listing, and the review UI can open a board's drawings from one place.
- The IR shard path does not change: `dist/ir/boards/<board_id>/view/<page_id>.json`
  ([ADR-0023](0023-ir-layer-on-disk.md) decision 2). Moving the source file changes no hash,
  because the shard layout is decoupled from the source tree
  ([ADR-0031](0031-project-tree-ownership-model.md) decision 9).

### 2. A view is authored source, not a derived artifact

The view lives in the repository, in `views/`, and not under `dist/`.

The reason is [ADR-0021](0021-schematic-view-layer.md) decision 2: the renderer draws and never
places. A view cannot be regenerated by the toolchain, because nothing in it knows how to choose
the positions. A file that cannot be regenerated is a source file; a source file that the project
owns belongs in the project tree.

What `AGENTS.md` §3 says about S1 — that it may be discarded — therefore means *discardable as
truth*, not *regenerable*: a board whose views are deleted is still a valid board, still
checkable, still exportable; it simply has no drawing.

### 2a. A view is hand-written, tracked, and outside the build

The three properties hold together, and each one rules out a different arrangement:

- **Hand-written.** A human (or an agent under instruction) moves the symbols, wires and
  labels. Nothing else writes them.
- **Tracked in the repository.** The adjustments are work worth keeping: they are what makes a
  sheet readable, and they are what the reviewer signed. A view that is not tracked is redrawn
  from nothing on every clone, and the review is repeated from the beginning.
- **Outside the build identity.** No artifact that is built depends on where a label sits, so a
  view shard is advisory (decision 3). The build and the drawing are versioned separately.

The tempting combination — *discardable, therefore derived, therefore in `dist/`* — is what this
decision rejects. A derived artifact is one the toolchain produces; a view is not. The other
tempting combination — *tracked, therefore part of the truth, therefore normative* — is rejected
by decision 3. "Tracked" and "normative" are different properties: a file can be tracked and
still not be part of the build.

The consequence worth stating plainly: **deleting `views/` does not invalidate anything that was
built.** The board remains valid, its hash is unchanged, and its manufacturing package stands.
Rebuilding the drawing is work, but it is not a rebuild of the design.

### 3. A view shard is advisory: it is not part of the build identity

This amends [ADR-0023](0023-ir-layer-on-disk.md) decision 4, which said that board shards are
always normative.

- The **project hash** covers the build: the schematic, the pcb, the symbols, the footprints,
  the families, the components, the library references, and the primary procurement
  selections.
- The **advisory hash** covers everything else in the project: the procurement alternatives and
  **the print pages**.
- The **board hash** covers the board's normative shards only. A page's drawing is not part of
  the board's build identity.

The criterion is unchanged and is applied consistently: *would changing this invalidate a signed
manufacturing package?* Moving a label does not, so a label move changes neither the project
hash nor the board hash, and a manufacturing package stays valid. Changing a pin table does, so
it changes both.

- A rendered page carries the **page shard's own `sha256`** as its `source_hash`, the same way
  a rendered symbol carries its shard's hash ([ADR-0014](0014-reference-renderer.md)). The
  drawing is therefore traceable to the exact file it was drawn from, without the drawing being
  part of the build identity. No new hash is introduced for this.
- A review record that cites a drawing cites the page's `source_hash`; a manufacturing record
  cites the board hash. The two do not have to move together.

### 4. A view that disagrees with the board is still an error

Classifying a page as advisory says nothing about whether it is *correct*. The cross-check that
[ADR-0021](0021-schematic-view-layer.md) requires — every instance, pin and net a view
references must exist in the board, and the view must not restate electrical facts — remains
mandatory, and a violation is an error.

The distinction is between *what the project asserts* and *what the project contains*. A page
that references a nonexistent instance asserts something false, and that is an error. A page
that is merely laid out differently asserts nothing about the build, and that is a difference in
content, not a defect.

This check is not implemented yet (`docs/backlog.md` F3).

### 5. The view still speaks the board's identity language

Unchanged from [ADR-0024](0024-level-tags-in-flattened-names.md) and
[ADR-0025](0025-flat-board-and-print-pages.md): a view references the board's ids verbatim, in
whatever shape they have — `R1`, `M1.R1`, `M1.VCC`, `U1.5`. A view does not define identity; it
borrows it. Moving the file to `views/` changes nothing about what it may reference.

## Consequences

- **A label move no longer invalidates a manufacturing package.** This is the substantive
  change: the hash of a build is the hash of the build.
- **The circuit layer is now homogeneous.** `design/` holds only circuit descriptions, so a
  tool that scans the circuit layer finds nothing it has to filter out. The drawing layer has
  its own root, and no directory name is both a file and a directory.
- **The page file is still a page of its board.** The grouping a reviewer relies on — one
  directory per board — is unchanged.
- **The price**: the board and its pages are in different roots, so a tool that wants both
  reads two. That is what `source.file` and the shard layout are for, and the review UI
  resolves the pair by board id.
- **The price**: a view is tracked but not part of the build, so the repository state and the
  build identity can diverge. That divergence is the point — it is what lets a reviewer adjust
  a sheet without invalidating a manufacturing package — but it means a drawing is never
  pinned by the project hash, only by its own shard hash.
- **The price**: a view is advisory, so the project hash does not identify "this project" in
  full — it identifies "this build". That was already the stated meaning of the hash
  ([ADR-0023](0023-ir-layer-on-disk.md) decision 4); the view simply joins the procurement
  alternatives on the side of content the build does not depend on.
- **The price**: `advisory_hash` now aggregates two different kinds of content — second sources
  and drawings. Both answer the same question ("what does this project contain beyond its
  build?"), and neither affects any artifact that carries the build identity.

## Alternatives Rejected

- **Keep the pages under `sch/<board_id>/`.** It keeps a description type inside another type's
  directory and keeps the `sch/hub.teda` / `sch/hub/` collision.
- **Keep the pages under `design/view/`.** It keeps the circuit layer homogeneous, which was the
  argument for the split, but it still puts a discardable drawing inside the directory that
  means "the truth". A reader of `design/` — human or tool — would have to know that one
  subdirectory of it is not part of the circuit. The root belongs beside the circuit, not under
  it.
- **Put the pages in `docs/`.** It would put them with the prose, but `docs/` is material the
  project *writes about* the design; a page is a drawing *of* the design. Mixing them puts
  reviewed artefacts and narrative in one directory.
- **Keep the pages under `sch/<board_id>/` but rename the board file** to `sch/<board_id>/
  board.teda`. It removes the collision and keeps the pages next to the board, but it breaks the
  "one board is one file, boards are listed as files" convention for every board, and it still
  mixes two description types in one directory.
- **Make view shards normative.** It would keep the project hash identifying "the project" in
  full, at the price that a reviewer's label nudge invalidates the signed manufacturing package
  for that board — the exact failure the normative/advisory split was introduced to prevent.
- **Give drawings their own third hash.** A `drawing_hash` per board would separate the two
  meanings cleanly, but it adds a hash concept, a manifest field and a stamping rule to solve a
  problem the page shard's own `sha256` already solves: a rendered page carries the hash of the
  file it was drawn from.
- **Move the views to `dist/` as derived artifacts.** They cannot be derived — the renderer does
  not place symbols ([ADR-0021](0021-schematic-view-layer.md) decision 2) — and a file under
  `dist/` is by definition something the project did not author.
- **Gitignore the views.** "Discardable" is about the truth, not about the work: the adjustments
  are what a reviewer spent effort on. Untracking them means redrawing every sheet on every
  clone and repeating the review from the beginning. They are tracked, and they are advisory.
- **Drop the page files and let the renderer lay out.** Rejected in
  [ADR-0021](0021-schematic-view-layer.md) decision 2, and nothing here changes it: a generated
  layout is not reviewable, and the readability checks would measure nothing.

## Open Points

  nonexistent instance is not yet reported. Decision 4 makes it mandatory; the work is
  outstanding.
- **The round-trip of the view layer** — `extract(render(view)) == view` — is not implemented.
  It is listed in `AGENTS.md` §10 as outstanding for the print-page renderer.

## Addendum (2026-10-22): a view is kept, and damage is repaired by hand

Closes the third open point of this record.

### 1. A view that exists is kept

A board may have no views at all — that is a valid board, and nothing is generated for it. But
a view that exists is **authored content**: it lives in the repository, and it is not disposable.

The reason is where the work is. A view is where a human moved a label out of the way of a
symbol, broke a crossing, or wrote a note that only makes sense to the people doing the review.
That work exists nowhere else. Nothing can regenerate it — the renderer draws, it does not
arrange — so "generate the drawing on demand" is not a feature that saves anything; it is a way
to lose the work.

### 2. Damage is repaired by hand, not by regeneration

A view that no longer matches its board — a moved instance, a renamed net — is a defect to be
reported and fixed by a person, not a file to be overwritten. The cross-check of decision 4
reports it; a human decides what the drawing should say.

Consequently: **no tool may overwrite a view file with a regenerated drawing**. The same rule
that governs rendering in general applies with full force here — a re-render never overwrites
manual adjustments — and for a view file the "adjustment" is the entire file.

### 3. This is a stronger statement than "the view is not build input"

Decision 2 and decision 3 keep the view out of the build identity: moving a label does not
change the project's hash. This addendum says more — the view is not a *cache* either. It is not
something that may be regenerated, dropped, or recomputed on demand. It is part of the project.
