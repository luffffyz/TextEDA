# IR Contract Reference (v0.19)

> Generated by `packages/ir/scripts/generate.ts` from `schemas/ir/v0.19/`; do not edit by hand.
>
> This table answers only two questions: **what type a field is** and **what its unit is**. Behavioral semantics are defined by `spec/` (the language-wide spec is `spec/teda.md`).
>
> Units are determined by field-name suffixes (ADR-0006 decision 7): `min_uv` is voltage (µV), `max_na` is current (nA), `value_mohm` is impedance (mΩ).

## `component`

- schema: `urn:texteda:ir:0.19:component`
- Semantic projection of one .teda component file. Pins must already be materialized in the IR: inline pins are copied verbatim; when `symbol` points to a third-party library that carries pin facts and the file omits `pins`, the parser expands them from the library and `pins_source` records the source. A self-built `symbol` stores only the view, without pin facts (ADR-0031), so a component pointing at a self-built symbol must inline `pins`.

## `pcb`

- schema: `urn:texteda:ir:0.19:pcb`
- Physical facts and rule intent of one PCB (layer B0). The required modules list names the globally unique project module instances this PCB implements (ADR-0069 D2); every placement, pad connection, trace, via, zone and rule resolves against those instances and the flattened project nets. No drawing parameters, silkscreen layout, fill caches or UUIDs; connectivity inside the PCB is decided by connect and the project schematic and is never back-derived from geometry. Copper continuity on this PCB remains separate from the root's interconnect facts: a shared project net_id or a root interconnect never creates copper here, and connect edges never imply an interconnect. See ADR-0016, ADR-0069, spec/pcb.md.

| `connect` | array<connect_edge> | yes | — | Explicitly declares which two pads have continuous copper between them — one of the sources of truth for connectivity. ## `schematic-view`

- schema: `urn:texteda:ir:0.19:schematic-view`

## `schematic`

- schema: `urn:texteda:ir:0.19:schematic`
- Project schematic IR: the one logical root of a project. It composes module descriptions from design/modules/; all component instances and electrical facts belong to modules, and the root has no component instances of its own. The IR stays flat for ordinary consumers: instances/nets/ports carry flattened names (<module_instance_id>.<local_id>), while the modules segment carries the module-instance ownership and module-port records needed to validate physical assignments and interconnect endpoints. Equal local net names in separate module instances never merge by themselves: a flattened project net exists only through the root's nets segment, and net-name equality never supplies a physical interconnect (ADR-0069 D1/D3). Source: design/sch/main.teda. See ADR-0069, ADR-0012, ADR-0006 decision 5.
