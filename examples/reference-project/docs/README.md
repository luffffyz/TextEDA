# reference-project

Reference project generated by `texteda init` and filled in afterwards. The project represents one
product with one logical root and two physical PCBs.

```
reference-project/
├── project.toml            # project metadata
├── assets/components/      # component descriptions, one subdirectory per category
│   ├── indicators/
│   ├── mcu/
│   ├── mechanical/
│   ├── passives/
│   ├── power/
│   ├── regulators/
│   └── sensors/
├── assets/symbols/         # in-house symbols, one subdirectory per device category
├── assets/footprints/      # in-house footprints, one subdirectory per package family
├── assets/procurement/     # selections for each physical PCB: primary/ and alternatives/
├── design/sch/main.teda    # the project's only logical root
├── design/modules/         # reusable module definitions; each owns its component facts
├── design/pcb/             # physical PCB implementations with explicit module ownership
│   ├── charger-buck.teda   # owns module instances M1 and M2
│   └── mcu-board.teda      # owns module instance M3
├── views/                  # flat, project-level advisory print pages
│   ├── <page_id>.view.teda
│   ├── modules/            # reusable module drawings
│   └── templates/          # reusable sheet furniture
├── external/               # material the project does not own: cached datasheets, imported sources
└── docs/                   # design documents, review records, simulation conclusions
```

There is deliberately no system-description directory. The logical root records project-wide
nets, ports, and cross-PCB interconnects; the PCB files record physical implementation.

## assets/components/

- `component_id` is the file name (without `.teda`), not a relative path: `assets/components/passives/r-0402.teda` ↔ `r-0402`.
- Subdirectories are only for categorization; the same `component_id` must be unique across the whole `assets/components/` tree.
- Describes part number, package, library symbol/footprint, pin table; `pins` is required when pointing at an in-house symbol, and may be omitted when pointing at a third-party library that carries its own pin facts (resolved by the library; inline wins).
- `params` declares the extra columns allowed for this component in module `instances` rows; the column semantics of a row are determined by the referenced component.
- Module definitions reference component ids and never inline component definitions; a missing file is an error. The project root references module instances and ports, not component files.
- No network fetches for libraries; the `<class>:` prefix of a symbol or footprint reference names the classification directory that holds the file (a symbol's device category, a footprint's package family), and a reference that resolves to no file is an error.
- Everything in this project is **in-house**: `assets/symbols/<category>/` + `assets/footprints/<family>/` are the source, and the directories are classifications, not libraries (ADR-0049). Library-level verification: `bun run lib:verify` (every component resolves, every library file compiles/exports/reads into KiCad, and the merged board of all footprints passes DRC cleanly).
- Examples: `tps7a2033pdbvr` (SOT-23-5, `assets/components/regulators/`), `tps5430ddar` (HSOIC-8, `assets/components/regulators/`), `r-0402` (generic resistor, `assets/components/passives/`), `xtal-8mhz-3225` (crystal, `assets/components/passives/`), `sw-ts-1187` (tactile switch, `assets/components/mechanical/`), `ch32v307vct6` (LQFP-100, `assets/components/mcu/`), `bq24610rger` (VQFN-24, `assets/components/power/`).
- `assets/components/` is a component library, and it is **curated**: a device file no module places and no procurement file selects is allowed (a part bought for a revision that has not been drawn yet), but it is reported (`library.device-unused`, a warning) because it is part of the project identity. `bun run texteda check` names it; nothing is deleted for you.

## docs/

- `datasheets/`: a **directory of local copies** of component datasheets, **not committed** (already excluded by `.gitignore`; vendor PDFs are copyrighted and are not distributed with the repository). File names correspond to components (`tps7a20.pdf` serves `tps7a2033pdbvr`); download them from the vendor websites as needed using the table in `mcu-board-components.md`. Components are always built from the datasheet, with pins and parameters taken from the local copy; the `datasheet` field in a component file records only the original URL.
- `mcu-board-components.md`: component selection for the MCU module and its physical PCB, load-capacitance/current-budget calculations, other key computations, and open items.
- `reviews/`: design-review records for the root logic, PCB implementation, and advisory drawings.
- Trial-run baselines (DRC report, Gerber list, and KiCad project files) are retained under `docs/trial-run/charger-buck/` when generated; the field-level IR → KiCad mapping is in `docs/guides/kicad-pcb-format.md`.
- Design documents and simulation evidence belong in `docs/`; conclusions are bound to the design version they verified.

## design/modules/

A module is a reusable circuit definition. It owns all of its component instances, local nets,
ports, and constraints; it is not a board-local schematic or a drawing page. An `instances` row is
`ref component_id [params...]`:

```
instances
  R1  r-0402  10k  ±1%
  U1  tps7a2033pdbvr
```

The package is not written in the `instances` row; it is determined by the referenced component,
for example `assets/components/passives/r-0402.teda`.

- `mcu-board.teda` defines the CH32V307VCT6 minimum system + TPS7A2033PDBVR 3.3V LDO: 5V in,
  3V3 out, and SWD via module ports. Component selection and calculations are in
  `mcu-board-components.md`.
- `charger-power.teda` defines the BQ24610 charging/power path, and `buck-5v.teda` defines the
  TPS5430 5V/3A buck. The project instantiates them as M1 and M2 on the charger PCB; their
  definitions remain independently reusable.

## design/sch/main.teda

`design/sch/main.teda` is the project's one logical root. It composes module definitions and owns
the project-wide module-instance ids, logical net membership, project ports, constraints, and
interconnect records. It has no component `instances` section: all component facts remain in
`design/modules/`.

The reference composition is:

```
modules
  M1  charger-power
  M2  buck-5v
  M3  mcu-board
```

The root `nets` section binds module ports into logical project nets such as `GND`, `SYS`, and
`VOUT`. It also declares the product's external ports. The two cross-PCB paths are explicit root
facts:

```
interconnects
  ic1  M2.VOUT  M3.DC_IN
  ic2  M2.GND   M3.GND
```

Only an explicit root `interconnects` record joins ports implemented on different PCBs. Equal net
names alone do not imply physical copper continuity: root net membership is a logical fact,
`interconnects` are the declared physical paths between boards, and each PCB's `connect` and
copper geometry establish continuity only within that PCB. A view can draw an existing
interconnect but cannot create one.

## design/pcb/

Each file under `design/pcb/` describes one physical PCB and has a required `modules` section that
lists the complete module instances owned by that PCB. Ownership is explicit and whole-module:

| PCB description | Module instances owned by the PCB | Module definitions |
|---|---|---|
| `design/pcb/charger-buck.teda` | `M1`, `M2` | `charger-power`, `buck-5v` |
| `design/pcb/mcu-board.teda` | `M3` | `mcu-board` |

Every project module instance is owned by exactly one PCB. A PCB may own several instances, and
the same reusable module definition may be instantiated on different PCBs, but one instance is
never split across PCBs. PCB placement, pad connections, traces, vias, zones, and rules resolve
against the assigned, flattened module instances. A PCB is not a second logical root.

`design/pcb/charger-buck.teda` is a **trial-run fixture for the KiCad export chain**, not the
production layout of the charger PCB:

- Only the 9 components of module instance `M2` (the buck) are placed; the components of `M1`
  (the charger power path) are not placed and are treated as variant status (not populated) per
  `spec/pcb.md` §5.2 rule 1. A production PCB must place all required instances.
- Physical references use qualified ids such as `M2.U1` and `M2.C1`; project net names such as
  `GND`, `SYS`, and `VOUT` remain the logical net identities.
- The coordinates of `place` / `connect` / `trace` / `via` were computed once by a prototype and
  then frozen. The IR stores explicit geometry, while connectivity is determined by the root
  logic and this PCB's `connect` section.

`design/pcb/mcu-board.teda` is a corresponding physical-PCB smoke/review fixture for module
instance `M3`, not a claim that the board is a fabricated production layout. Its placements and
connectivity exercise project-root binding and whole-module ownership.

## views/

Project advisory pages are flat: `views/<page_id>.view.teda` has no PCB or board parent. The
conventional `views/main.view.teda` is a topology overview of module boxes, ports, and declared
interconnects; detail pages may place any subset of the project's flattened components. Page
divisions are for drawing and review only, and pages carry no electrical or copper facts. They can
be deleted and redrawn without changing the root logic, PCB implementations, netlists, or
physical ownership. `views/modules/` contains reusable module drawings and `views/templates/`
contains sheet furniture; neither directory creates board-scoped pages.

## Conventions

- `project.toml` is the project entry point; `[project].name` matches the directory name by default.
- All description files share the `.teda` extension; the first line distinguishes `component` / `schematic` / `module` / `pcb` / `view` / `module_view` / `sheet_template`.
- `design/sch/main.teda` is the only schematic root. `design/modules/` holds reusable electrical definitions, `design/pcb/` holds physical implementations, and `views/<page_id>.view.teda` holds flat project advisory drawings.
- Module-instance ownership is declared by each PCB's `modules` section, not inferred from a file name, module definition, equal net name, or view page. Cross-PCB paths are declared by root `interconnects`; equal names alone never join boards.
- Every description file carries the same language version (see [ADR-0002](../../../docs/adr/01-language/0002-one-language-version-number.md)). A file's number is the language generation it was written against; `[project].format` carries the same number.
- Component references in `variants` use the stable `component_id`, not refdes.

## Next steps

1. Keep project electrical facts in `design/modules/` and compose their instances only in `design/sch/main.teda`.
2. For each physical PCB, list every wholly owned module instance in its `design/pcb/<pcb_id>.teda` `modules` section; do not split an instance.
3. Add explicit root `interconnects` for each cross-PCB port path. Do not rely on equal net names to imply copper continuity.
4. Add or revise flat advisory pages under `views/<page_id>.view.teda`; drawing changes must not duplicate logic.
5. Run `bun run check` to verify.
