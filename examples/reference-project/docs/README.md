# reference-project

Reference project generated by `texteda init` and filled in afterwards.

```
reference-project/
├── project.toml            # project metadata
├── assets/components/      # component descriptions, one subdirectory per category
│   ├── indicators/
│   ├── mcu/
│   ├── mechanical/
│   ├── passives/
│   ├── power/
│   ├── regulators/
│   └── sensors/
├── assets/symbols/         # in-house symbols, one subdirectory per device category (view; pin facts live in assets/components/)
├── assets/footprints/      # in-house footprints, one subdirectory per package family (geometry source of truth)
├── assets/procurement/     # part selection per board: primary/ (in the build) and alternatives/
├── design/sch/             # schematic descriptions: one file per board
├── design/modules/         # reusable module descriptions a board composes
├── design/pcb/             # PCB description, may come later; this project has one trial-run fixture, charger-buck.teda
├── design/system/          # multi-board connection descriptions, one file per system
├── views/                  # print pages of a board's drawing, views/<board_id>/<page_id>.view.teda
├── external/               # material the project does not own: cached datasheets, imported library sources
└── docs/                   # design documents, review records, simulation conclusions
```

## assets/components/

- `component_id` is the file name (without `.teda`), not a relative path: `assets/components/passives/r-0402.teda` ↔ `r-0402`.
- Subdirectories are only for categorization; the same `component_id` must be unique across the whole `assets/components/` tree.
- Describes part number, package, library symbol/footprint, pin table; `pins` is required when pointing at an in-house symbol, and may be omitted when pointing at a third-party library that carries its own pin facts (resolved by the library; inline wins).
- `params` declares the extra columns allowed for this component in `instances` rows; the column semantics of a row are determined by the referenced component.
- `sch` references ids only and never inlines component definitions; a missing file is an error.
- No network fetches for libraries; the `<class>:` prefix of a symbol or footprint reference names the classification directory that holds the file (a symbol's device category, a footprint's package family), and a reference that resolves to no file is an error.
- Everything in this project is **in-house**: `assets/symbols/<category>/` + `assets/footprints/<family>/` are the source, and the directories are classifications, not libraries (ADR-0049). Library-level verification: `bun run lib:verify` (every component resolves, every library file compiles/exports/reads into KiCad, and the merged board of all footprints passes DRC cleanly).
- Examples: `tps7a2033pdbvr` (SOT-23-5, `assets/components/regulators/`), `tps5430ddar` (HSOIC-8, `assets/components/regulators/`), `r-0402` (generic resistor, `assets/components/passives/`), `xtal-8mhz-3225` (crystal, `assets/components/passives/`), `sw-ts-1187` (tactile switch, `assets/components/mechanical/`), `ch32v307vct6` (LQFP-100, `assets/components/mcu/`), `bq24610rger` (VQFN-24, `assets/components/power/`).
- `assets/components/` is a component library, and it is **curated**: a device file no board places and no procurement file selects is allowed (a part bought for a revision that has not been drawn yet), but it is reported (`library.device-unused`, a warning) because it is part of the project identity. `bun run texteda check` names it; nothing is deleted for you.

## docs/

- `datasheets/`: a **directory of local copies** of component datasheets, **not committed** (already excluded by `.gitignore`; vendor PDFs are copyrighted and not distributed with the repository). File names correspond to components (`tps7a20.pdf` serves `tps7a2033pdbvr`); download them from the vendor websites as needed using the table in `mcu-board-components.md`. Components are always built from the datasheet, with pins and parameters taken from the local copy; the `datasheet` field in a component file records only the original URL.
- `mcu-board-components.md`: component selection for the MCU board, load-capacitance/current-budget calculations and other key computations, and open items.

## design/sch/

An `instances` row = `ref component_id [params...]`:

```
instances
  R1  r-0402  10k  ±1%
  U1  tps7a2033pdbvr
```

The package is not written in the `instances` row; it is determined by `assets/components/passives/r-0402.teda`.

`mcu-board.teda` is a single-file board (it declares `ports`, no pages): CH32V307VCT6 minimal system + TPS7A2033PDBVR 3.3V LDO, 5V in, 3V3 out, SWD via board-level ports. Component selection and calculations are in `mcu-board-components.md`.

`charger-buck.teda` is a single-file board: `BQ24610 charging/power path + TPS5430 5V buck`, **one physical board** sharing one BOM and one PCB. `refdes` and net names are unique inside the board, and the two circuits are told apart by numbering and by net prefix:

- The power path is `C1`..`C18`, `D1`..`D4`, `L1`, `NTC1`, `Q1`..`Q5`, `R1`..`R22`, `U1`; its nets are `AC_*`, `ADAPTER_*`, `BAT*`, `PH`, `SYS`, `TS*`, `VBAT`, `VCC`, `VFB`, `VREF`, …
- The buck continues the board's numbering: `C19`..`C22`, `D5`, `L2`, `R23`, `R24`, `U2`; its nets carry a `BUCK_` prefix (`BOOT`, `BUCK_PH`, `BUCK_VFB`) and it shares the board's `GND`, `SYS` and `VOUT` rails.
- The board-level `ports` section declares the board's external terminals (`AC_RET` / `BAT` / `DC_IN` / `GND` / `VOUT_5V`); `SYS` is an internal rail and is not exposed.

### Print pages (the drawing layer)

The board's drawing does not fit on one sheet, so it is partitioned in the **view** layer, not in the logic: `views/charger-buck/*.view.teda` are print pages. They name the board's instances and nets directly, carry no electrical facts, and can be deleted and redrawn at any time without touching the board.

- `views/charger-buck/charger-power.view.teda`: placement study of the power path; the wire runs are laid out during review.
- `views/charger-buck/buck-5v.view.teda`: the buck, every net drawn as wires.

Decision records are in the repository's `docs/adr/schematic/0012-one-flat-schematic-per-board.md`; syntax is in `spec/teda.md` §7 and `spec/schematic-view.md`.

## design/pcb/

`design/pcb/charger-buck.teda` is a **trial-run fixture for the KiCad export chain**, not the production PCB of the `charger-buck` board:

- Only the 9 components of the buck are placed; the components of the power path are not placed and are treated as variant status (not populated) per `spec/pcb.md` §5.2 rule 1. A production PCB must place all instances.
- Instance ids and net names are the board's own: `U2`, `C19`, … and `GND` / `SYS` / `VOUT` / `BOOT` / `BUCK_PH` / `BUCK_VFB`.
- The coordinates of `place` / `connect` / `trace` / `via` were computed once by a prototype and then frozen; the IR stores only explicit geometry, with connectivity determined by the `connect` section and the sch.
- Trial-run baselines (DRC report, Gerber list, KiCad project files) are in the repository's `docs/trial-run/charger-buck/`; the field-level IR → KiCad mapping is in `docs/guides/kicad-pcb-format.md`.

## Conventions

- `project.toml` is the project entry point; `[project].name` matches the directory name by default.
- All description files share the `.teda` extension; the first line distinguishes `component` / `schematic` / `pcb` / `system` / `view`.
- `design/sch/`, `design/pcb/`, and `design/system/` are split by **description type**, not by board; the same board uses the same file name in `design/sch/` and `design/pcb/` (`charger-buck.teda`), distinguished by directory. A board's print pages are the exception and live in `views/<board_id>/<page_id>.view.teda`.
- One board = one file, one BOM, one PCB. Do not split a board into several schematic files; partition the drawing instead.
- Every description file carries the same number: the language has one version, not one per description type (see [ADR-0002](../../../docs/adr/language/0002-one-language-version-number.md)). A file's number is the language generation it was written against; `[project].format` carries the same number.
- `design/pcb/` may be empty; when the PCB description is missing, sch↔pcb binding verification is skipped and the report marks it "not verified".
- Component references in `variants` use the stable `component_id`, not refdes.
- Design documents and simulation evidence go in `docs/`; conclusions are bound to the design version they verified.

## Next steps

1. Board schematics live in `design/sch/<board_id>.teda`, one file per board; the drawing is partitioned in `views/<board_id>/<page_id>.view.teda`.
2. When a physical implementation is needed, create a file of the same name under `design/pcb/`.
3. Once the board's external interface is settled, add connector components on the corresponding nets; `ports` needs no changes.
4. Run `bun run check` to verify.
